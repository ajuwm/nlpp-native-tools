# 开发历程

> 这份文档记录**怎么走到今天的**，包括走过的弯路。
> 结论在 `README.md`，这里写的是**过程**——尤其是那些反复出现的错误模式。

---

## 起点

目标：**不转格式**，直接用 New Love Plus+ 自己的资源（`.smes` / `.smat` / `.bone` / `.texi` / `.mot`）
渲染角色，最后做成一个能用游戏原生动画摆姿势的场景编辑器。

前提：只做解析器，**不含任何游戏资源**。

---

## 第一阶段：资源能读出来了

按 `img.bin` 的 PACK/SERI 容器结构取文件，然后逐个格式解：

| 格式 | 怎么确认的 |
|---|---|
| `smes` 模型 | 顶点/法线/UV/权重/索引字段逐一对照 |
| `bone` 骨骼 | 254 根共享骨架；每根 0x24 字节 `T@0x00 R@0x0C S@0x18` |
| `smat` 材质 | **MATC 颜色是 A,R,G,B 不是 R,G,B,A** —— 读错会整体发青 |
| `texi` 纹理 | 5 种格式，**137 处逐字节验证**（ETC1 / ETC1A4 / RGBA8 …） |
| 背景 | `bs_*.jpg` 1356 张，512×672，**需要 90° 旋转** |
| 相机 | `cam_ang_*.cdb` 70 字节 = 35 个 u16；`[143]` 是零点，eye=1,2,3，target=4,5,6 |

**这一阶段比较顺，因为有像素级反馈——渲染出来对不对，一眼就知道。**

## 第二阶段：`.mot` 动作（真正的地狱）

### 关键决定：去读游戏的 `code.bin`

`.mot` 靠猜是猜不出来的，所以转为**反汇编游戏代码**。

`code.bin` 是 **8,126,464 字节的明文 ARM**，`VA = 文件偏移 + 0x100000`。
写了个 `dis_arm.py` 做 VA ↔ 偏移换算和常量搜索。

**这一步是对的。** 后面所有硬结论都来自这里：

```
0x00740A68  ldrh  nk          记录的关键帧数
0x00740A78  ldrh  mask        通道掩码
0x00740A80  tst   #0x100 …    通道数 = popcount(mask & 0x1FF)
0x00740BF8  mul   r0,r0,r6    每个关键帧 nch 个浮点
0x00740C9C  vsub + vmla       线性插值（没有切线）
0x00740CA0                     refs 的 bit31 选池
0x0069B26C  tst #0x100 …      位 → 槽的完整分配
0x0069B904  常量 256/2π        三角度 → 旋转矩阵
0x00740D08                    骨骼查询 obj->[8]->[0x0C][记录号]
```

**「旋转组 = 位 5/4/3」由三处独立确认**（分发器写入点、求值循环的读取偏移、结构布局）。

### 但接下来连续踩坑，而且都是同类

#### 坑 1：改动没生效（出现 3 次）

| 现象 | 原因 |
|---|---|
| 在 `compose.py` 改了 `per`，渲染完全不变 | `sweep_body.py` 里把 `per` **硬编码成 1** |
| 修好骨骼映射，渲染 sha256 一模一样 | `nlp_mot.py` 里有**三处**骨骼赋值，只改到两处 |
| 轴扫描 6 种排列结果完全相同 | 用**位号**去查**轴索引**字典，静默匹配不到 |

**共同点：改动作用在错误的键、错误的副本、或根本没被调用到的分支上。**
**表面看「跑通了」，实际什么都没发生。**

**⇒ 后来固定了一条规矩：任何扫描，先用一个「已知必然产生差异」的极端变体验证扫描本身有效。**

#### 坑 2：用间接判据代替直接判据

我判断「每个关键帧占 `nch` 个浮点」的依据是：
记录的**长度公式与相邻记录间隙吻合**。

**那个公式之所以吻合，是因为两种步长在观测样本上恰好同解。**

直到直接打印池里的原始浮点，才看到真相：

```
按 stride=3 读通道 0：[-4.394, 80.811, -2.875, -0.045, 0.121, …]   ← 每隔一个跳到 80.8
按 stride=6 读通道 0：[-4.394, -2.875,  0.121, -4.881, -2.817, …]   ← 平滑
```

**⇒ 真实步长是 `2 × nch`。这一步解决了两个从早期就困扰的问题：**

- 「**六根不同腿骨带同一个 ~80.9 值**」—— 那是交错采样的假象
- 「**角色永久蹲姿**」—— 膝弯一直显示成 80°

**⇒ 直接判据（时间轴上是否平滑）永远优于间接判据（长度吻合）。**

#### 坑 3：从文件名推断语义

| 文件名叫 | 我以为是 | 实测驱动的是 |
|---|---|---|
| `m_lower011` | 下半身 | **头发骨骼 78~96** |
| `m_skirt_000` | 裙摆 | **头发骨骼 78~96** |

**⇒ 直接查数据（`bone_owner.py`：列出每个网格的顶点绑定到哪些骨骼）才得到真相。**

**⇒ 教训：语义必须查证，不能从命名推断。**

#### 坑 4：取样偏差（出现 2 次）

早期随手取了 `m_00011_40.mot`，之后**几十轮都在围绕它判断解码器对错**。

后来扫全库才发现：

```
1701 个身体动作，1663 个同时驱动手臂和小腿
而我一直在用的 m_00000_40 —— 手臂交集只有 2 根骨，是个「腿部动作」
```

第二次是拿 `m_09070_21` 出图代表「动作」——而那个动作**只有小腿在动**。

**⇒ 单样本判断整条链路，是错的。**

#### 坑 5：测量错对象

我用 `(wp[i] @ binv[i])[:3,3]` 当作「骨骼位置」——
那是**蒙皮相对矩阵**，空姿势下它的平移是原点。

**⇒ 因此早期所有膝角数字（40°↔140°、98.1°）全部作废。**

正确做法是 `wp[i][:3, 3]`。

#### 坑 6：把「静态偏移」当成「动画位移」

测到「手臂顶点相对绑定移动 128 单位」，我写成了「手臂确实被放下来了」。
逐帧打印才发现：

```
所有帧：手臂平均 Y = 124.6 ~ 124.7   ← 每一帧都一样
```

**⇒ 那是相对绑定姿势的静态偏移，不是动画。手臂根本没在动。**

#### 坑 7：编造解释

看到 130° 的颈骨旋转，我写「这是舞蹈/战斗类的夸张动作」。

**⇒ 这游戏是恋爱模拟，根本没有战斗和舞蹈动画。** 那是我编的。

## 第三阶段：现在的状态

### 站得住的结论

全部来自 `code.bin` 反汇编或**数据自身**：

- 容器头 / 记录布局 / 通道数 / 池路由 / 线性插值
- 位 → 分量（旋转 = 位 5/4/3，三处独立确认）
- **关键帧步长 = `2 × nch`**（依据：值的平滑性）
- 记录 → 骨骼表（`值 = 骨骼号 + 225 × bank`；依据：`m_hand000` 精确落在手骨 49~63）
- 骨 → 网格归属（实测）

### 明确标为「未验证」

- **姿势绑定**、**腿部动作** —— 能跑通、不崩，但**从未与游戏内画面对照过**
- 所以 README 里不写「正确」，只写「能跑通」

### 卡住的地方

`.mot` 的**骨骼语义**：

- 手臂网格绑定的 `191/194/203/210~224` 段几乎不被任何动作驱动
- `m_lowerNNN` / `m_skirt_NNN` 驱动的是头发骨骼
- 找不到「手臂自然下垂」的基础姿势（绑定姿势是 T-pose，平静动作的手臂幅度只有 ~18°）
- **身体动作 ↔ 分层变体的配对规则不在 `code.bin`（`.mot` 字符串命中 0），也不在 577 个 `.dbin2` 的明文里**

### 试过但失败的（避免重复劳动）

- 15 个 `m_upperNNN` 层全部 —— 都会把手臂折成平板或让头脱离
- 3 个驱动完整手臂骨骼的 `_10` 动作 —— 套用后角色形变
- 记录↔骨骼配对整体偏移扫描（60 种）
- 绝对/相对旋转语义对照
- 轴排列 6 种全扫
- bank 0/1 消融
- 分层动作旋转的绝对语义修正

---

## 一句话总结

**格式本身已经解出来了**（每一步都有游戏代码或数据自身作证）；
**卡住的是「这些骨骼编号对应身体的哪个部位、以及谁驱动谁」这一层语义。**

**如果你要接手，建议先从 `diagnostics/` 读起** ——
那些脚本记录了每个结论是**怎么被证伪或证实的**，比读格式说明更能避开我踩过的坑。
