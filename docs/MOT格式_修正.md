# `.mot` 动作格式：已解（2026-10-11/12 修正）

> 本文记录把「动作骨骼语义」这一层彻底解开的全过程与证据。
> **结论：格式已经完整解开，旧版 README 第二节里有 5 条结论是错的。**
>
> 所有结论都在真实数据上验证过（本机 CIA 解出的 `img.bin`：2207 个 `.mot`、254 根骨骼）。

## 0. 一句话总结

旧版本卡住的根因是**6 个独立的数据解码错误叠加**（第 6 条是最后一击）：

| # | 旧结论 | 真相 | 怎么证实的 |
|---|---|---|---|
| 1 | `.mot` 表值 = 骨骼号（`-225` if `>=225`） | 表值是**骨骼 ID**，要查 `BONE` 里那张 u32[254] ID 表 | ID 303 解出骨骼 6，其值 `T=(12.0,-2.8)` 正好等于骨骼 6 的绑定平移 |
| 2 | 每个通道每个关键帧占 **1** 个浮点 | `pool A` 条目是 **3 个浮点**，偏移 = `3*ref`；`pool B` 才是 1 个 | 全库：refs 全在 B 的 64277 条**全是 nk==1**；全在 A 的 41574 条**全是 nk>1** |
| 3 | `nk>1` 的平移是增量 | 平移**一律是绝对位置** | 骨盆 `T.y=80.13`，而绑定平移是 80.91 —— 那就是身高 |
| 4 | 旋转是"度" | 旋转是**弧度**，渲染器要"度" | 手骨绑定 ±1.709：当 1.7° 时整套 hand rig 等于没转 |
| 5 | 每顶点 1 组骨骼权重 | 步长 0x40 = 44 + **4 字节索引 + 4 个 float 权重** | `weights=[0.230,0.750,0.020,0]` 只读了 0.23 |
| 6 | 三角度按 `Rx·Ry·Rz` 组合 | 正确顺序是 **`Rz·Ry·Rx`（ZYX）** | 见 §6.1：大角度下角色会整个翻过去，换成 ZYX 后同一个动作变成自然的"坐下→起身→走" |

外加：**关键帧步长就是 `nch`**（旧 README §2.5 的"2×nch 是本仓库最重要的修正"是错的）。

## 1. 骨骼 ID 表（最关键的一条）

`BONE` 头部第三个字段（旧代码记作 `unk_off`）指向一张 **u32[count] 骨骼 ID 表**：

```
BONE 头:  'BONE' | u32 count | u32 id_table_off | u32 parent_off | u32 bone_off
          id_table[骨骼号] = 骨骼 ID
```

* `img.bin` 里**所有部件**（头发/连衣裙/裙子/腿/手/脸）的这张表**逐字节一致**，
  ID 范围 10..322，254 个 ID 互不相同 → **全局 ID 空间**。
* `.mot` 的 `header+0x0C` 表存的就是这些 ID，必须查表换算成扁平骨骼号。

**证据（双向可验证）**：单关键帧记录存的是绝对绑定平移，于是映射可被直接检验：

```
m_skirt_000 的 ID 序列 [303,304,305,306, 307..310, 311,84,312,313, ...]
   → 查表 → [ 6, 236,237,238,  7..241,   8, 242,243,244, ...]
   骨骼 6 的绑定 T = (0.00, 12.00, -2.80)   记录里正是 (12.0, -2.8)   ✓
   骨骼 7 的绑定 T = (0.00, 12.00, 13.51)   记录里正是 (12.0, 13.51)  ✓
```

六片三段裙摆（根 6..11 + 每片 3 段）逐条对上。

**为什么会误以为 `-225` 能用**：`m_hand000` 的 ID 274..288 减 225 恰好是**左手** 49..63，
而真值是**右手** 210..224 —— 同样是 15 根连续骨，**形状相同、对象不同**。

## 2. 两个池的元素宽度不同

```
refs[i] & 0x80000000  →  pool B, 浮点偏移 = ref & 0x7FFFFFFF   (1 个浮点)
refs[i] & 0x80000000 == 0 → pool A, 浮点偏移 = 3 * ref          (3 个浮点: 值 + 两条切线)
```

全库统计（不是抽样）：

| 记录类型 | 指向 pool B | 指向 pool A |
|---|---|---|
| `nk == 1`（分层动作） | 64,277 | 0 |
| `nk > 1`（身体动作） | 0 | 41,574（另有 7,680 条混合：常量通道用 B、动画通道用 A）|

混合记录典型形态（`i_00010.mot`，nk=14）：

```
refs = [0B, 1B, 0A] [0B, 1B, 1A] [0B, 1B, 2A] ...   ← 通道 0/1 是常量(B)，通道 2 每帧一个新条目(A)
```

旁证：A 条目三个浮点是 `(值, 切线, 切线)`，切线大小正是值的逐帧差分。

---

## 3. 关键帧步长 = `nch`

纯结构判据（不依赖任何语义）：

```
offs[i+1] - offs[i] ?= 4 + 2*nk + pad4 + 4*nk*nch
```

在 **111,382 条记录**上：`4*nk*nch` 命中 **111,382**；`4*nk*2*nch` 命中 **0**。

⇒ 旧文档所谓「stride = 2×nch 是最重要的修正」是**间接判据**（"平滑性"）得出的错误结论；
真正的原因是第 2 条：refs 指向的是 3 浮点条目。

---

## 4. 平移 = 绝对位置

```
m_00010_40 记录 0（骨盆，骨骼 2）第一帧 6 通道：
   T = (7.48, 80.13, -4.28)      R = (-0.04, 0.18, 0.10)
骨骼 2 的绑定平移 = (0.00, 80.91, 0.77)
```

`80.13` 就是身高。只有把平移当**绝对坐标**才讲得通；旧代码把 `nk>1` 的平移当增量叠加，
角色被抬高约一倍（"悬空"）。

---

## 5. 旋转 = 弧度，且渲染器要"度"

* `.bone` 手骨 49..63 / 210..224 的绑定旋转是 `(±0.25, 0, ∓1.709)`：
  当 **1.7°** 用时整套 hand rig 等于没转（手臂一摆、手就相对手腕扭掉）；
  当 **1.709 rad = 98°** 时才是正常的手骨朝向。
* `.mot` 的旋转值同样是弧度。`nlp_render.rotate_axis(axis, deg)` 内部 `math.radians(deg)`，
  所以进渲染器前统一 `× 180/π`。

---

## 6. 通道位 → 分量

```
bit 8/7/6 -> T.x/T.y/T.z      bit 5/4/3 -> R.x/R.y/R.z      bit 2/1/0 -> S.x/S.y/S.z
通道数 nch = popcount(mask & 0x1FF)，按**位号降序**写入 refs[k*nch + c]
```

旧代码把 `bit4/bit3` 映射成 `R.z/R.y`（当年用"高度保持不变"这个**间接**判据选的）。
在骨骼映射与条目宽度修正后，那个顺序会把手臂折到不自然的角度。
（`LP_ROLD=1` 可切回旧顺序对照。）

**被排除的假设**：旋转的欧拉顺序**不是**扭曲来源 —— 用"手腕→指尖"与"肘→腕"夹角作判据，
六种欧拉顺序 + 轴角在同一批动作上差异 **< 3°**。

（⚠️ 这条只在**小角度**下成立。见 §6.1：大角度下顺序是决定性的。）

### 6.1 三角度 → 矩阵的组合顺序：`ZYX`（第 6 个 bug）

**症状**：一批动作渲染出来人**整个翻过去 / 蜷成球**（`m_09340_00` 在 t=44 头朝下）。

**关键约束（由用户提供）**：这是 galgame，**没有翻滚/空翻类动作**。
所以"人倒过来"一定是解码错误，不是游戏本来如此 —— 这条把排查方向一下子定死了。

**定位过程**：

1. 把骨盆（骨骼 2）的旋转关掉再渲染 → `m_09340_00` 立刻变成正常的"蹲下/起身" ✓
   ⇒ 问题出在**根骨骼的大角度旋转**上。（对照开关 `LP_NOROOT=1`）

2. 看骨盆逐帧原始数据（弧度）：`R.x ≈ R.z` 在**每一帧**都几乎相等
   （-1.68/-1.70、-2.90/-2.95、0.27/0.30），且 `R.y` 单调增到 1.65 rad（≈95°）。

3. 用**头部相对骨盆的高度**作判据扫六种组合顺序（`tools/euler_large.py`）：

```
m_09340_00   头-骨盆最小高度差:  XYZ -27.0(头到骨盆下方=翻了✗)  XZY +14.2  YXZ +23.4
                                YZX  +5.6   ZXY  -6.9   ZYX +39.9 ← 最优
m_09550_21                      XYZ +14.6   ...        ZYX +44.7 ← 最优
```

4. 改用 `ZYX` 渲染 `m_09340_00`：**变成完全自然的"坐→起身→走"** ✓✓，
   同时待机动作、8 个手部层（小角度）渲染结果不变 ✓。

**结论**：`R_local = Rz(rz) · Ry(ry) · Rx(rx)`，即先绕 X、再绕 Y、最后绕 Z
（矩阵乘法的书写顺序是 ZYX）。默认已改为 ZYX，`LP_EULER=XYZ` 可切回旧行为对照。

**为什么之前没发现**：手臂/手指的旋转多在 30~90°，不同顺序差别只有几度，
肉眼与"手型是否合理"都分不出来；只有骨盆这种**90° 以上**的旋转才会把差别放大成
"翻跟头"。

## 7. 附带的第 5 个 bug：蒙皮只用了 1/4 权重

顶点步长 **0x40 = 64 字节**，正好是：

```
位置 12 + 法线 12 + 切线 12 + UV 8 = 44
+ 4 个骨骼索引字节 (u8[4])        = 48
+ 4 个 float 权重    (f32[4])     = 64   ✓
```

实测每个顶点 4 个权重**和恰为 1.0**：

```
v0  boneBytes=[0,1,0,0]  weights=[0.350, 0.650, 0.000, 0.000]
v1  boneBytes=[0,1,2,0]  weights=[0.230, 0.750, 0.020, 0.000]
```

旧代码 `nw = skinning_mode`（值为 1）→ **只读第 1 组**，归一化后整个顶点只跟随 1 根骨。

* **为什么一直没被发现**：绑定姿势下 `wp · binv = I`，权重对错渲染结果完全一样 ——
  **绑定姿势验证不了权重**。
* **症状**：一摆动作，关节处顶点被单根骨拽走，袖子在肩部塌成尖刺。

## 8. 身体动作 ↔ 分层变体：配对规则

**规则一：`_skirt` 层按 PACK 分组 + 同名后缀配对。**

`img.bin` 的 PACK 容器本身就是"动作集"：

| 包内 .mot 形态 | 包数 |
|---|---|
| `(m_<动作>_<变体>)` 单独一个 | 873 |
| `(m_<动作>_<变体>, m_<动作>_<变体>_skirt)` 成对 | **167** |
| `(m_upper#)` / `(m_lower#)` / `(m_hand#)` / `(m_skirt_#)` 变体集 | 15 / 19 / 8 / 13 |

实例（pack 2639）：

```
m_01520_30.mot  m_01520_31.mot  m_01520_32.mot
m_01520_30_skirt.mot  m_01520_31_skirt.mot  m_01520_32_skirt.mot
```

⇒ **同一个包里的 `m_<动作>_<变体>_skirt` 就是它的裙摆层**，不需要额外查表。
276 个 `_skirt` 文件**全部**能找到同名身体动作（孤儿 0 个）。

**已落地**：`native/compose.py` 的 `load_layers()` 会在同一包里自动找 `_skirt` 伙伴并叠加。
效果：坐姿动作里裙子不再被腿穿出来，而是自然张开盖住腿。对照开关 `LP_NOSKIRT=1`。

> **这解释了画面里"腿是扭曲的"这个观感**：裙子停在绑定姿势、腿却按动作折叠，
> 腿就从裙子里穿出来。不是骨骼解码问题，而是没驱动原本就该驱动裙子的那一层。

**规则二：`m_upperNNN / m_lowerNNN / m_skirt_NNN / m_handNNN` 是按服装的变体集**（各自独立成包）：

* `m_upper`(15)：手臂+手（长袖/短袖/无袖…）
* `m_lower`(19)：一部分驱动腿 12-18、123-126（裤装），一部分驱动裙骨 6-11、236-253
* `m_skirt_`(13)：裙骨 6-11、236-253
* `m_hand`(8)：右手 210-224

数量（15/19/13/8）与服装模型数（`m_01_*` 116、`m_02_*` 49、`m_03_*` 17）对不上 →
不是按模型下标选，而是按**服装类别**选。选择表**仍未定位**（见 §12）。

## 11. 手部（手指）专项核查

**结论：身体动作里带的手部姿势是"默认手型"，且与游戏自带手部层逐值相同 → 解码正确。**

```
骨骼绑定 R（度）: 210=(14.4, 0, 97.9)  211=(0.3, 0, 93.0)  215=(0.3, 0.9, 3.3)

m_00010_40（待机） 210=(2.0, -0.2, 103.3)  215=(0.3, 3.3)  216=(8.2)
m_08400_32（起身） 210=(2.0, -0.2, 103.3)  215=(0.3, 3.3)  216=(8.2)
m_09600_00（坐）   210=(2.0, -0.2, 103.3)  215=(0.3, 3.3)  216=(8.2)
m_hand000（游戏手部层）210=(2.0, -0.2, 103.3)   ← 与上面三者完全一致
```

* 手指**基础节** 210：绑定 97.9° → 动作 103.3°，只差 **5.4°**；
* 手指**指节** 215：绑定 3.3° → 动作 3.3°，**无额外弯曲**。

⇒ 画面里"手指微曲"是游戏设计的手型（放松半握），不是解码把手指拧了。
把 8 个手部层分别套到手模型渲染（`tools/hand_layers.py` → `out/hand_layers.png`）
得到 **8 个明显不同的合理手型**（微曲/握拳/指点/挥手…）。
其中 `m_hand002` 是极端姿势（指根 163.3°、指节 119.1°），会塌成一块平板，待确认。

**注意**：不能拿"绑定姿势的手"和"套动作后的手"直接比形状 —— 绑定是 T-pose（手臂水平），
套动作后手臂已下垂，相机固定时手的朝向完全不同，看起来"变形"是正常的。

## 13. 可复现的最小验证

```bash
# 绑定姿势（应当完全正常）
python quickstart.py --img img.bin --out bind.png

# 动作（修正后：手臂自然下垂、手型正常、双脚落地）
LP_MOTION=m_31003_40.mot python native/compose.py --img img.bin \
        --out walk.png --frames 0,14,28,42,56,70
```

对照开关（用于复核本文每一条结论）：

| 环境变量 | 作用 |
|---|---|
| `LP_IDMAP=0` | 退回旧的 `-225` 规则 |
| `LP_ROLD=1` | 退回旧的 R 轴顺序（bit4→R.z, bit3→R.y）|

## ★★ 动作是"四段一组"的闭环（2026-10-17 确证）

**这是本项目对 `.mot` 库最重要的结构性发现** ✓ —— 待机**不是**一个文件循环 ✗，
而是**四个文件串成一个闭环** ✓：

```
m_XXXXX_40  过渡段   →  m_XXXXX_41  保持段
                          ↓
m_XXXXX_43  保持段   ←  m_XXXXX_42  过渡段（转回另一边 ✓）
```

以 `m_00010` 为例（实测像素差，越小越"接得上"）：

| 衔接 | 像素差 |
|---|---|
| `_40` 末 → `_41` 首 | **0.02** ✓ |
| `_41` 末 → `_42` 首 | **0.02** ✓ |
| `_42` 末 → `_43` 首 | **0.07** ✓ |
| `_43` 末 → `_40` 首 | **0.02** ✓ |

每段自身的首尾差说明了它的角色 ✓：过渡段 **15.1**（大 ✓）、保持段 **0.02**（小 ✓）。
**四处衔接全部 < 0.1，而循环内部帧间差均值 1.51** ⇒ 串起来播放完全无缝 ✓✓

**全库验证**（`tools/group_chain_test.py`）：含 `_40.._43` 变体的 **37 组里 31 组构成闭环** ✓，
典型各组四处衔接最大仅 **0.08** ✓：

✅ m_00010  0.05 0.05 0.03 0.03     自身首尾 32.25  0.05  32.27  0.03
